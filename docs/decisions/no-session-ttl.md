# 决策：去掉会话 TTL，连接"能用就一直用"

> 2026-10-24 更新：传输层已换成全局 `fetch`（见 [fetch-over-http2.md](fetch-over-http2.md)）。
> 「没有 TTL」的结论不变，但下文中关于 unref/ref 记账、`isUsable()` 检查、
> `close` 事件清缓存的部分已随 `http2` 删除——现在失效路径只有一条：
> 请求抛网络错误 → `invalidateSession()`。

## 结论

| 改动 | 内容                                                                |
| ---- | ------------------------------------------------------------------- |
| 删除 | `SESSION_TTL_MS`（5 分钟）、`cache.ts`、`retire()` 及其 `WeakSet`   |
| 保留 | `unref/ref` 请求计数、`close` 事件清缓存、`isUsable` 检查、失败重建 |
| 简化 | `cache` 从 `{ session, ts }` 变为 `Session \| null`                 |
| 超时 | 单次请求 `12s → 6s`，且**超时主动 `invalidateSession()`**           |

失效路径从 5 条降到 4 条，且剩下 4 条全部可由一次请求或一个事件观测到。

## 为什么删 TTL

### 1. 在真实部署形态下是死代码

一次查询 1~2s，进程寿命通常只有几秒；5 分钟的 TTL **永远不会触发**。
它不是"收益低"，是"从未运行过"。

### 2. 它防不住真正的问题

观测到过一次（本机 → cn.bing.com）：连接空闲 **90 秒**后，`closed=false`、
`destroyed=false`、没有任何 close/error 事件，但发出的请求 30 秒内
没有任何 response/error/end —— 连接已被静默丢弃。

同样的 90s 空闲实验第二次却完全正常（请求 211ms 成功），所以这是**偶发**
而不是固定阈值。正因为它偶发，更可能落在 90s~5min 的任意位置——而 5 分钟
的 TTL 在这个窗口里根本不会触发。**TTL 想防的故障发生在它触发之前，
且没有固定的时间规律。**

### 3. 成本确定，收益不确定

每次 TTL 到期重建要重做首页握手 + 新连接，实测约 **+0.85s**
（冷启动 1653~~1775ms vs 缓存命中 880~~1003ms）。

### 4. 可审计性

TTL 是唯一"静默发生、且与故障无关"的失效路径：一切正常时它也会
突然多付 0.85s，而且没有日志、没有事件，只能靠读代码知道。
短进程场景下，它带来的只有认知负担。

## 为什么 6 秒超时

超时的目的不是"用户体验上限"，而是**判定连接/网络已死**。

20 次连续查询的端到端耗时（每次含两遍请求 + 解析）：

| 指标                         | 值     |
| ---------------------------- | ------ |
| 中位                         | 1063ms |
| p90                          | 1210ms |
| max（冷启动，含首页 + 握手） | 1730ms |

单次 HTTP 请求典型 **200~600ms**，6s 是典型值的 10 倍以上。
正常 Bing 不可能 6s 不响应；6s 还静默，基本可以判定连接已死或网络故障。

> 这是本机网络的观测。慢网下 400KB 页面需要约 67KB/s 才能 6s 内下完，
> 正常服务器带宽远高于此。

## 关键配套：超时必须重建连接

只改超时数值是不够的。旧 `search.ts` 的 catch 里：

```ts
if (e instanceof SearchHttpError) {
    if (e.kind === 'fatal') return empty // 超时是 retryable，走到这里就结束了
}
```

超时被分类为 `retryable`，**不会** `invalidateSession()`。于是重试会
继续用同一条死连接：3 次全部超时（旧参数 12s×3 ≈ 36s，新参数 6s×3 ≈ 18s），
最后返回空结果——重试毫无意义。

修复：`SearchHttpError.status === 0`（超时）时主动 `invalidateSession()`，
下一次 attempt 强制重建。这样静默死连接的代价从"18s + 空结果"变成
"6s + 重建后的正常结果"。

## 不采用的替代

| 方案                              | 否决理由                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 空闲阈值（`lastUsed` > 60s 重建） | 语义上比年龄 TTL 更对，但当前没有长驻进程场景；等出现再加                                                                     |
| 每次新建连接、用完即关            | 失去 490ms/查询的复用收益                                                                                                     |
| 置 null 让 GC 回收连接            | 不成立：活跃 socket handle 是 GC 根，健康连接对象不会被回收（50 次 full GC 实测仍存活），fd 只有 `destroy()` 或进程退出才释放 |
| 保留 TTL 但改短（如 60s）         | 高频使用时周期性多付 0.85s，且仍防不住 90s 的静默丢弃                                                                         |

## 边界

- 同一进程隔 >90s 再查一次：首次可能 +6s（超时后重建重试，结果仍正确）。
  这是当前方案唯一的代价。
- 若下游出现长驻进程（MCP server / Electron / Web 后端），再加
  `lastUsed` 空闲阈值（60s）——它对应"闲置被丢弃"这个真实故障，
  而不是"会话活得太久"这个没有证据的担忧。
- cookie 不再定期刷新。短进程无影响；长驻进程的 cookie 老化暂无证据
  表明有害，也无可证无害。

## 验证

```bash
pnpm test                              # typecheck + 离线 96 + 在线 29~31（卡片随机）
pnpm test:live        # connection.test.ts 的「不调关闭函数时进程自然退出」
```

空闲 90s 实验（两次）：

- 第一次：请求 30s 无任何事件 → 确属静默死连接；
- 第二次：`closed=false`，请求 211ms 正常返回。

6s 超时相对正常请求（200~600ms）有 10 倍以上余量；即使误杀，重建重试
的成本也远低于挂 12s。

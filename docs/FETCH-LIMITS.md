# web_fetch 的能力边界与成本

`downloadHTMLToMarkdown`（沙盒里的 `web_fetch`）是下游最容易失控的一环。
本文记录**它在哪里失效、失效的代价是多少、以及怎么修**。

> 这些结论与选哪个入口无关——任何下游接进来都会撞上同一批问题。
> 一次 20 题实验的 7.71 元账单里，**62% 花在本文描述的失效上**。

## 一、PDF 是最大黑洞

### 1.1 Bing 确实标了 `[PDF]`，而解析器没读

Bing 会给文档型主结果打文件类型标记，DOM 位置是 `h2` 的**兄弟节点**：

```html
<li class="b_algo">
    <div class="b_title">
        <span class="sb_doct_txt">[PDF]</span>
        <!-- 国际版是 sb_doct_txt b_float -->
        <h2><a href="…/090631-01.pdf">决策树 - 清华大学出版社</a></h2>
    </div>
</li>
```

因为标记在 `h2` 之前、不在标题里，`text(h2 a)` 天然不含它；
**旧实现从未读过 `sb_doct_txt`**，所以 `WebPage` 上没有任何文件类型字段。
这不是「解析错了」，是从来没解析。

272 个 `b_algo` 里 4 个带标记，**全部是真实 `.pdf` 链接，没有反例**。
（标记文本本身不进任何输出字段，class 是多值，要按类名匹配、按文本定类型。）

### 1.2 但这个缺口为什么致命

`downloadHTMLToMarkdown` **根本没有解 PDF**——它把 PDF 二进制当文本读，
再当 HTML 摊平。实测两个样本：

| URL               | 产出         | 标题层级 | 开头                                                       |
| ----------------- | ------------ | -------- | ---------------------------------------------------------- |
| `arxiv.org/pdf/…` | 461,910 字符 | **0**    | `%PDF-1.7 1 0 obj << /Type /ObjStm /Filter /FlateDecode …` |
| `…/99RubinCM.pdf` | 419,319 字符 | **0**    | `%PDF-1.2 7 0 obj << /Type /Encoding /Differences[…`       |

**一条链路串起来：**

> 丢掉 `[PDF]` 标记 → 无差别抓 PDF → 转换出 40 万字符垃圾
> → 没有标题层级切不开 → 整页直出 → 上下文爆掉

模型在 reasoning 里反复说的 “PDF extraction is garbage”，看到的确实是垃圾。

### 1.3 代价

单次 PDF 抓取平均 **211,262 字符**，是 HTML 的 **12 倍**。
一次实验里 13 次 PDF 抓取吃掉 **43% 的抓取字节**，而检索结果里 `.pdf` 只占 **3.5%**（36/1028）。

按「本轮 prompt 增量 × 该 PDF 占本轮字符比例 × 剩余轮数」归因：

| run       | 总 token  | PDF 成本  | 占比    | PDF 次数 | 其中被引用 |
| --------- | --------- | --------- | ------- | -------- | ---------- |
| math-3/cn | 4,923,261 | 4,746,039 | **96%** | 3        | 0          |
| math-1/cn | 3,976,230 | 3,863,157 | **97%** | 3        | 0          |
| lit-1/cn  | 875,891   | 782,497   | 89%     | 2        | 1          |
| math-2/cn | 605,088   | 488,708   | 81%     | 1        | 1          |

**PDF 总成本 11,170,786 token = 主实验的 62%；其中被引用的只占 11%，纯浪费 55%。**

### 1.4 修法：必须两步一起做（第 1 步已完成，第 2 步没有）

| 步骤      | 做什么                                                                          | 状态                                                                                |
| --------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 1. 解析层 | 读 `.b_title .sb_doct_txt` → 定类型 → `PdfPage`                                 | **已实现**（`DOC_TYPE_MARKER`），细节见 [PARSING.md](PARSING.md) 的「文档型主结果」 |
| 2. 抓取层 | `content-type` 是 `application/pdf` 或 URL 以 `.pdf` 结尾时，**不走 `html2md`** | **未实现**                                                                          |

**只做第 1 步反而更糟**：模型现在能看到 `type: 'pdf'`，会更倾向于想
「既然是 PDF 那肯定有原文，我去抓」——而抓回来还是垃圾。

第 2 步要做到的是：让抓取层直接返回类似
`{ error: 'binary_pdf', hint: '该链接是 PDF，请改用摘要或 HTML 版本' }`，
**给模型一个结构化的「这条路不通」信号**，而不是让它从乱码里自己推断。

> 这也是 §9.2 那个「说了垃圾还继续抓」的直接解药：模型不是不知道，是没人告诉它。

**判别只认标记，不看 URL 后缀。** 我们是 Bing 的封装，Bing 打什么标就信什么标；
后缀只是站点自己的命名习惯（`/serve?id=42` 也可能是 PDF）。
现有样本里两者 3/3 重合，**互相印证但无法互相证伪**——所以离线用例锁的是
「标记决定 type」这个语义，包括「标记在而 URL 不是 `.pdf` → `pdf`」与
「URL 像 PDF 而没有标记 → `page`」两个方向。

## 二、`buildOutline` 的 `null` 兜底

切片规则是「从 h1 往下找第一个『块数 ≥ 2 且最大块 ≤ 60K』的层级」：

```ts
for (let level = 1; level <= 6; level++) {
    const blocks = blocksAt(lines, headings, level)
    if (blocks.length < 2) continue      // 只有一个标题 → 跳过
    if (maxSize > maxBlock) continue     // 单块超 60K → 跳过
    return { ... }
}
return null                              // 全都不满足 → 整页直出
```

PDF 转 Markdown 后通常没有标题层级，或只有一个 h1 包住全文。于是每一层都 `blocks.length < 2`，
返回 `null`，走「该页面没有可用于切分的标题结构，只能返回全文」，几十万字符一次性进上下文。

**这条兜底原本是合理设计**（「不切宁可不切，避免给半节内容」），
但它假设「切不开的页面不会太大」——PDF 恰好推翻这个假设。

### 2.1 正确的做法不是取消兜底，是给兜底加盖

| 位置                              | 改什么                                  | 为什么                                       |
| --------------------------------- | --------------------------------------- | -------------------------------------------- |
| `buildOutline` 返回 `null` 的分支 | 只回前 8,000 字符 + 说明                | 保住「不切宁可不切」的语义，但限制单次注入量 |
| 短页全文直出分支                  | 上限 8,000 字符                         | 同理                                         |
| 取节分支                          | 超预算就只回目录                        | 让模型细化范围，而不是硬塞                   |
| 软线（预算 80%）                  | 任何 > 60K 的页面直接拦，不再走字符估算 | 估算在 PDF 上会低估 4 倍（见 §3）            |

## 三、字符 → token 的换算：不能按均值估

实测 79 个样本的 token/字符比：

| 统计量 | 值   |
| ------ | ---- |
| 中位数 | 0.61 |
| P90    | 1.00 |
| 最大值 | 1.06 |

分布是双峰的：

| 内容类型           | token/字符      |
| ------------------ | --------------- |
| 正常 HTML          | 0.23 ~ 0.27     |
| **PDF 二进制垃圾** | **1.04 ~ 1.06** |

**垃圾比正常文本贵 4 倍。** 因为 BPE 分词器无法压缩随机字节流，
每个字符几乎都被编码成独立 token；而正常中文/英文有大量高频片段共享 token。

这就是为什么预算估算必须用 **1.1 而不是中位数 0.61**：
下载前分不清两者，按均值估会把 41 万字符的 PDF 判成 18 万而放行——**实测真的发生过**。

代价是正常 HTML 会被高估约 4 倍，所以要用「软线」补偿（见 §4）。

## 四、会话级上下文预算

量的是**当前这一轮 prompt 的 token 数**，不是累计消耗（累计本来就会一直涨，不是危险信号）。

```
每轮开头 reportContextTokens(usage.prompt_tokens)   ← 服务端口径，不本地估

web_search / web_fetch 入口：used ≥ 200K → 全部工具停用，回执要求直接写答案
web_fetch 内部三处事前拦（字符 × 1.1 估算）：
  短页全文 / outline=null（PDF 走这条）/ 取节，超预算就只给前 8,000 字符或目录
软线 160K：任何 > 60K 的页面直接拦，不再走估算
循环层：超预算且本轮工具全失败 → contextStopped，撤掉 tools 强制作答
```

### 4.1 五次迭代才收敛

同一个用例（math-3 国际版，当初 0 轮无答案那题）：

| 版本                      | 轮     | 峰值 prompt     | 总 token  | 答案     | 触发       |
| ------------------------- | ------ | --------------- | --------- | -------- | ---------- |
| 崩溃（无护栏）            | 0      | 1,336,328 → 400 | 1,336,328 | **无**   | —          |
| 事后检查                  | 5      | 329,723         | 678,561   | 4,092 字 | 硬线       |
| + 短页/取节事前拦（0.45） | 9      | 382,359         | 491,880   | 3,985 字 | 未触发     |
| + 兜底也拦（0.45）        | 10     | 283,245         | 789,972   | 5,460 字 | 硬线       |
| **终版（1.1 + 软线）**    | **17** | **61,649**      | 579,986   | 3,098 字 | **未触发** |

前三次失败的原因都是**低估注入量**：

| 版本              | 漏在哪                                               |
| ----------------- | ---------------------------------------------------- |
| 事后检查          | 只在返回后检查，不看下轮会注入多少                   |
| + 短页/取节事前拦 | **漏了 `outline = null` 的兜底分支**（PDF 全走这条） |
| 0.45 系数         | 41 万字符的 PDF 被判成 18 万，放行后峰值仍到 28 万   |

终版最值得看的是**峰值 prompt 从 38 万降到 6.2 万**，而轮数反而从 10 涨到 17。
这不是矛盾——护栏让模型换了策略：

| 轮    | 动作           | 返回                          |
| ----- | -------------- | ----------------------------- |
| 5     | 抓 arxiv 论文  | **8,000 / 355,487**（被截断） |
| 6     | 抓另一篇       | **8,000 / 200,550**（被截断） |
| 10    | 抓同一篇要目录 | 2,179 / 267,490               |
| 11–14 | 分 4 次取节    | 每次 3.5K~7.2K                |

**它从「一次吞 35 万字符」变成了「先要目录，再按节取 4 次」。**
这正是切片功能原本设计的使用方式，只是过去从没被逼到这条路上。

### 4.2 200K 这个值怎么来的

模型上限是 1,048,576。取 200K 的理由不是「留 5 倍余量」，而是：

- 一次 200K 的 prompt 在实测里已经能装下 5~8 个抓取页面，足够回答绝大多数问题
- 超过 200K 之后，**每多一轮的成本开始指数化**（每轮重发整个上下文）
- 单次请求 1,336,328 撞 400 的案例里，前一轮就已经是 100 万——早就该停了

## 五、两个入口的成本结构（去掉 PDF 之后才看得清）

原始账单：国内版均 668,992 token，国际版均 247,576——差 2.7 倍。
**但这个差距几乎全部来自 PDF**：国内版抓了 10 次 PDF（成本 1,007 万），国际版 3 次（110 万）。

三种未来情形：

| 情形                        | 说明                              | 国内版均 token | 国际版均 token | 倍数      |
| --------------------------- | --------------------------------- | -------------- | -------------- | --------- |
| **现状**                    | PDF 当二进制抓，整页直出          | 668,992        | 247,576        | **0.37×** |
| **A：PDF 能正确解出**       | 文本量降到 15%                    | 240,784        | 198,576        | **0.82×** |
| **B：PDF 完全跳过**         | 见到 `[PDF]` 就不抓               | 165,218        | 189,929        | **1.15×** |
| **C：A + 大 HTML 也按节切** | 顺带治理 55 万/110 万字符的全文页 | 240,784        | 176,733        | **0.73×** |

### 5.1 修好之后，成本优势翻转，质量优势不翻转

| 指标                   | 现状             | 情形 A       | 情形 B           |
| ---------------------- | ---------------- | ------------ | ---------------- |
| 均成本                 | 国际版省 63%     | 国际版省 18% | **国内版省 13%** |
| 质量（成本归一后胜负） | 国际 13 : 国内 1 | 同左         | 同左             |

情形 B 下「谁更便宜」翻转成国内版，但只翻 13%——而质量上是 13 比 1。

### 5.2 分领域看，质量与成本几乎全部反向

情形 A 下的均成本：

| 领域     | 国内版  | 国际版  | 谁便宜   | 质量谁胜     | 同向？      |
| -------- | ------- | ------- | -------- | ------------ | ----------- |
| 编程     | 68,788  | 76,486  | 国内 10% | 打平         | ✅          |
| 中国史   | 297,448 | 373,881 | 国内 20% | **国际 4:0** | ❌ **反向** |
| 非遗     | 190,324 | 112,150 | 国际 41% | 国内微胜     | ❌ 反向     |
| 外国文学 | 197,564 | 285,480 | 国内 31% | **国际 2:0** | ❌ **反向** |
| 数学     | 449,797 | 126,989 | 国际 72% | 国内 3:0     | ❌ 反向     |

**五个领域里只有编程是质量与成本同向，其余四个全部反向。**

历史段最典型：国际版贵 26%，但它直引《汉书》《魏书》原文；
国内版便宜 20%，却停在百科综述。**这 26% 买的是证据。**

### 5.3 所以「国际版更贵」这个反对理由，大部分是工具缺陷的假象

> **修好 PDF 之后，两个入口的成本差从 2.7 倍降到 1.2 倍以内，
> 剩下的 20~30% 是「读到原文」的明码标价。**

成本差可以在工程上继续压（切节、缓存、预算），
但「没读原文」这件事没法在工程上补——模型只能编。

## 六、抓取利用率：钱花得值不值

定义：**进入最终答案的检索字节 ÷ 总共注入上下文的字节**。

三个可量化的层次：

| 层        | 判据                                        | 能算吗                                    |
| --------- | ------------------------------------------- | ----------------------------------------- |
| L1 引用率 | 答案 URL 集合 ∩ 抓取 URL 集合               | ✅ 完全可算                               |
| L2 采用率 | 答案里的具体数字/原文句是否出现在抓取正文中 | ✅ 需存正文（当前 trace 只存 chars 长度） |
| L3 因果率 | 去掉这一页，答案会变差吗                    | ❌ 要重跑，成本高                         |

### 6.1 L1 结果

| 口径                 | 国内版    | 国际版    |
| -------------------- | --------- | --------- |
| 严格（URL 完全相同） | **37.0%** | **88.2%** |
| 宽松（同域名被引）   | 41.9%     | 90.3%     |

全部 227 次抓取里，被引用的 3,896,515 字符、未被引用的 2,507,889 字符——
**四成的抓取字节是白读的**。

但要说清：这个差距不是搜索质量造成的。首搜 top5 命中率两侧是 1.10 与 1.11，
统计上没有区别。**差别发生在「模型接下来点哪一页」**，而那是落地页选择问题。

### 6.2 同一个工具，贡献率能从 100% 掉到 2%

| 题        | 抓取字符 | 有效    | 贡献率    |
| --------- | -------- | ------- | --------- |
| math-4/cn | 11,638   | 11,638  | **100%**  |
| math-2/cn | 479,144  | 478,982 | **99.9%** |
| ich-2/cn  | 50,648   | 47,000  | 93%       |
| math-1/cn | 975,578  | 19,265  | **2.0%**  |
| math-3/cn | 673,587  | 19,092  | **2.8%**  |

**math-2 读了 46 万字符的 arxiv PDF，贡献率 99.9%；
math-1 读了 70 万字符的会议论文集 PDF，贡献率 2%。**

两者都是「大 PDF」，一个值一个白读。区别是：
math-2 问的是「最新上界是多少」，那篇 PDF 就是提出新上界的原始论文，**不可替代**；
math-1 问的是「依赖哪个选择公理片段」，答案在 MathOverflow 的 1.5 万字符回答里，
那 70 万字符只是「可能相关」。

> **贡献率不看入口，看「模型选的落地页是不是该问题的证据主场」。**

## 七、量化的代理指标

「答案对不对」是终局判据，但它不告诉你钱花在哪、卡在哪。
下面这些能从 trace 里直接算出来，不需要人工评分。

### 7.1 搜索次数与边际收益

| 搜索次数 | runs | 均 token  | 均答案   | 每千 token 产出 |
| -------- | ---- | --------- | -------- | --------------- |
| 1–2      | 10   | 43,064    | 2,542 字 | **59.0 字**     |
| 3–4      | 8    | 76,726    | 2,783 字 | 36.3 字         |
| 5–6      | 8    | 230,786   | 2,588 字 | 11.2 字         |
| 7+       | 14   | 1,085,219 | 2,943 字 | **2.7 字**      |

**从 1–2 次加到 7+ 次，答案只长了 401 字，成本涨了 25 倍。**
第 5 次搜索之后几乎不再带来新答案。

### 7.2 「术语召回」拆成三层，只有前两层能自动算

| 层          | 定义                               | 能自动算 | 结论                       |
| ----------- | ---------------------------------- | -------- | -------------------------- |
| **L1 覆盖** | 题目术语锚点出现在结果标题里的比例 | ✅       | 两边都 ~100%，**无区分度** |
| **L2 名次** | 首个命中出现在第几条               | ✅       | 两边都是 1~2，**无区分度** |
| **L3 可用** | 命中的那条最终是否被读、被引用     | ✅       | **差异全在这里**           |

**L1 与 L2 完全无法区分两个入口**——「术语召回」在字面意义上不是瓶颈，
Bing 两版都能把 `Kummer` / `QPACK` / `Tate-Shafarevich` 正确匹配到相关页。

推荐只留一个指标：

> **首搜有效条数** = 首搜 top5 中「最终被抓取且被答案引用」的条数（0~5）。
> 本次均值 **1.0**，方差 0.9。

它同时惩罚三件事：召回错、结果不可读、模型判断失误。不依赖人工评分。
坏处是把「入口的锅」和「模型的锅」混在一起。

### 7.3 拆锅：搜索给错了 vs 模型没选对

| 情形     | 判据                                          | 出现次数                 |
| -------- | --------------------------------------------- | ------------------------ |
| 搜索的锅 | 首搜 top5 里没有一条可读的（全垃圾站/全 PDF） | **0 次**                 |
| 模型的锅 | 首搜 top5 里有可读的，但模型没抓              | **12 次**（39 次运行里） |
| 都对     | 首搜就抓对                                    | 5 次                     |
| 后续补上 | 首搜没抓，靠改写补回来                        | 22 次                    |

**一次「搜索给错了」都没出现。** 每次首搜 top5 里都至少有 1~2 条可读且相关的页面。

典型例子（code-1 国内版）：首搜 `Rust Pin std::pin 自引用结构体 为什么需要` 的 top5 里，
第 3、4 条就是知乎的两篇 Pin 讲解；模型一条都没抓，转而搜了英文关键词，
才抓到 Microsoft 的 RustTraining。最终答案引用的 4 条里，**没有一条来自首搜**。

这不能简单判成「模型失误」——它是在用「自己认为最权威」的先验去定向，
而不是信 Bing 的排序。这在工程上合理，在成本上是灾难。

### 7.4 平台率：曝光 → 点击 → 采用

| 平台                           | 曝光 | 点击   | 点击率  | 采用 | 点击→采用 |
| ------------------------------ | ---- | ------ | ------- | ---- | --------- |
| 官方文档                       | 28   | **27** | **96%** | 25   | **93%**   |
| 非遗网                         | 15   | 9      | 60%     | 8    | 89%       |
| 古籍站                         | 69   | 21     | 30%     | 15   | 71%       |
| wiki系                         | 31   | 9      | 29%     | 8    | 89%       |
| 文学/全文                      | 31   | 14     | 45%     | 7    | 50%       |
| 百度系                         | 138  | 18     | 13%     | 8    | 44%       |
| 学术                           | 86   | 10     | 12%     | 4    | 40%       |
| 知乎                           | 67   | 10     | 15%     | 8    | 80%       |
| **CSDN**                       | 23   | **0**  | **0%**  | 0    | —         |
| **今日头条**                   | 35   | **0**  | **0%**  | 0    | —         |
| **文档站**（道客/豆丁/原创力） | 17   | **0**  | **0%**  | 0    | —         |

**模型确实在区分**：官方文档点到 96%、采用 93%；CSDN/头条/文档站共 75 次曝光，
**一次都没点**。这不是抓不动，是主动跳过。

但伤害不在「抓取失败」，在于**名次**：

| 平台     | 曝光 | 平均名次 | 第 1 名占比 |
| -------- | ---- | -------- | ----------- |
| 官方文档 | 28   | **2.3**  | 36%         |
| 百度系   | 138  | 2.7      | 26%         |
| 今日头条 | 35   | 2.7      | **29%**     |
| CSDN     | 23   | 2.9      | **22%**     |

**今日头条以 29% 的第 1 名占比、100% 零点击，是最纯粹的位次浪费。**
它排在第 8 位时模型根本不会看；排在第 1 位时，模型得先扫过它才能找到真正的源。

## 八、「答案长度是常数，输入是变量」

这是最能改变判断的一条观测。

| 量       | 均值     | 标准差  | CV       |
| -------- | -------- | ------- | -------- |
| 答案长度 | 2,803 字 | 693     | **0.25** |
| 抓取字节 | 164,215  | 264,658 | **1.61** |

**输入量的变异是输出量的 6.4 倍。**

更直接的对照：

| 组                | 抓取字节（均值） | 答案长度（均值） |
| ----------------- | ---------------- | ---------------- |
| 抓最多的 5 个 run | 789,120          | 2,705 字         |
| 抓最少的 5 个 run | 13,843           | **2,880 字**     |
| 比值              | **57 倍**        | **0.94 倍**      |

**抓 57 倍的量，答案反而短 6%。**

相关系数全在 0 附近：

| 自变量          | r（与答案长度） |
| --------------- | --------------- |
| 抓取字节        | **0.005**       |
| token 总量      | **−0.059**      |
| reasoning token | 0.06            |

领域均值能解释的残差 SD 是 672，总 SD 是 693 —— **领域只解释了 6% 的方差**，
剩下 94% 是模型自己的输出先验。

### 8.1 三个推论

**推论一：继续喂材料不会让答案更好，只会让账单更高。**
这是上下文预算最硬的证据——不是「可能浪费」，是「一定浪费」。

**推论二：token 效率指标测的不是搜索质量，是浪费程度。**
math-1/cn 的 0.9 字/千 token 不是因为它答得差（3,401 字，中上），
而是因为它读了 97 万字符来产出这 3,401 字。

**推论三：「读得多答得好」不成立。**
真正让答案变好的是「读到对的那一页」，而这与读多少页无关：

| run                  | 抓取字节 | token     | 答案     | 关键材料                   |
| -------------------- | -------- | --------- | -------- | -------------------------- |
| math-2/international | 25,529   | 75,530    | 1,868 字 | 5 个小页，全部被引用       |
| math-1/cn            | 975,578  | 4,976,230 | 3,401 字 | 2 篇关键论文**都没被引用** |

math-2 读 2.5 万字节就分清了 186 / 240 / 246 三档口径；
math-1 读 97 万字节，却把最该看的 MathOverflow 之外的论文全漏了。

### 8.2 唯一的例外，正好划出规则边界

hist-2/international 写了 4,818 字（领域残差 +1,939）。
它为什么能突破 2,800 字的先验？**因为材料里有可整段引用的一手原文**（《魏书》《资治通鉴》）。

看证据密度（引文 + 书名 + 年份 + 数字，每千字）：

| run                  | 引文 | 书名 | 证据密度 | 答案长度 |
| -------------------- | ---- | ---- | -------- | -------- |
| hist-2/international | 57   | 37   | **35.3** | 4,818    |
| hist-3/international | 15   | 26   | 24.8     | 2,336    |
| math-3/cn            | 5    | 0    | **3.4**  | 2,039    |
| code-1/cn            | 9    | 0    | 2.5      | 3,655    |

**但 hist-3/international 是个必须点明的反例**：证据密度 24.8（第二高），
答案只有 2,336 字。所以「密度高 → 答案长」不成立。

正确的因果是反过来的：

- **密度是材料的属性**：手上有多少可引用的一手内容（《旧唐书》原文、法条号、RFC 条款）
- **长度是模型的属性**：它先决定写多长，再从材料里挑着填

hist-2/intl 与 hist-3/intl 材料质量接近（都用识典古籍 + 24shi.wiki + 维基文库），
但模型给前者写 4,818 字、后者只有 2,336 字——**同一入口、同一天、同类材料，长度差一倍**。
这比任何相关系数都更直接地说明：长度是模型的自由变量。

### 8.3 所以真正的目标不是「少抓」，是「抓到可引用的原文」

| 材料类型                                | 答案行为                         | 例                                |
| --------------------------------------- | -------------------------------- | --------------------------------- |
| 可引用原文（古籍、法条、RFC、源码文档） | **变长**、证据密度高             | hist-2/intl 4,818 字 / 密度 35.3  |
| 二手综述（百科、博客、CSDN）            | 停在先验长度、密度低             | math-3/cn 2,039 字 / 密度 3.4     |
| 二进制垃圾（PDF）                       | 停在先验长度、还多烧 10 倍 token | math-1/cn 3,401 字 / 497 万 token |

一句话：

> **原文密集的题（文学、史学）吃「原文可获得性」；
> 推导密集的题（数学、编程）吃「术语召回」。**
> 这是两个正交互补的能力，所以「哪个入口更好」没有全局答案。

## 九、模型的因素：它尽力了，但有三个系统性弱点

### 9.1 它确实在区分信源

| 行为           | 数据                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 跳过低质源     | CSDN/头条/文档站 75 次曝光，**0 次点击**                                |
| 优先官方源     | 官方文档 28 次曝光、27 次点击、93% 采用                                 |
| 目录回取       | 拿到 toc 12 次，**9 次回去取章节**（75%）                               |
| 失败后改写     | 引号使用率从第 1-2 轮的 3% 升到第 6+ 轮的 68%（cn）/ 81%（intl）        |
| 自我纠错       | math-1/cn 轮 4 明说 “The PDF fetch was garbage”，随后改抓 HTML 页并成功 |
| 显式标注不确定 | 答案里会写「仅取到检索摘要」「未逐字核对」                              |

**模型知道自己在读垃圾，并且没有假装读过。**

### 9.2 弱点一：说了垃圾还继续抓

| 轮  | 动作                | 本轮 reasoning 有抱怨吗 |
| --- | ------------------- | ----------------------- |
| 3   | 抓 `99RubinCM.pdf`  | 无                      |
| 4   | 抓 `weakmw.pdf`     | **有**                  |
| 5   | 抓 handwiki（HTML） | **有**                  |
| 6   | 抓 `Tatereview.pdf` | 无（抱怨之后仍继续）    |

它在第 4 轮就知道 PDF 是垃圾，第 6 轮又抓了一个。**知道不等于改变策略。**

不能全怪模型：`web_fetch` 的返回值里没有任何「这是二进制」的结构化信号，
模型只能从「看起来像乱码」推断；而那个判断在下一轮的上下文里被新的乱码覆盖。
**这正是 §1.4 那两步修改要解决的。**

### 9.3 弱点二与三

**弱点二：答案长度是常数。** 见 §八，这是本节之外的独立发现。

**弱点三：首搜结果不决定用词，但也不引导深挖。**
首搜 top3 标题的词汇对后续搜索词的重合度平均只有 **5%**。
说明模型**没有**被首搜带偏（好事），但后续改写是「凭先验重新问」而非「沿结果深挖」——
这正好解释了它为什么经常抓错页：它按自己的关键词体系去找，而不是按 Bing 给出的线索去找。

### 9.4 模型是比入口更大的变量

| 对照                                   | 数值                                     |
| -------------------------------------- | ---------------------------------------- |
| 首搜 top5 命中率（cn vs intl）         | 1.10 vs 1.11 —— 无差别                   |
| 同题两入口答案相似度（2-gram Jaccard） | **0.17** —— 各自组织，不是复述           |
| 同题两入口答案长度的 r                 | **0.37** —— 「答多长」主要不是题目决定的 |

**入口决定了「能拿到什么」，模型决定了「答成什么样」，两者独立性很高。**

## 十、可落地的动作

| #   | 动作                                                              | 预期收益               | 代价            |
| --- | ----------------------------------------------------------------- | ---------------------- | --------------- |
| 1   | 解析 `sb_doct_txt` → `fileType`，并在抓取层拦截 `application/pdf` | 省 55% token           | 5 行 + 一处分支 |
| 2   | 给 `web_fetch` 加会话级累计字符预算                               | 挡住剩余的大页注入     | 已实现（§四）   |
| 3   | 把「答案长度」从效率指标里剔除，改用「证据密度」                  | 指标不再被模型先验污染 | 改文档          |

第 3 条容易被忽略但很重要：现在所有「每千 token 产出字数」的排名，
测的都是「模型这次写了多长」与「读了多少」的比值，而前者几乎是常数。
真正该看的是**证据密度**（每千字有多少条可核实的引文/数字/条款号），
它才反映「这一页材料有没有被真正转化成论据」。

## 十一、一句话总结

> **一次实验的 7.71 元账单里，62% 花在 PDF 上，55% 是纯浪费；
> 而模型写了多长的答案是常数，与花了多少钱几乎无关（r = 0.005）。**

所以优化的方向不是「让模型少读」，而是：

1. **不要给它读不了的东西**（PDF 拦截）
2. **不要让它一次吞太大**（会话预算）
3. **让它更容易落到可引用的原文上**（这是选入口的问题，见 [ENTRANCES.md](ENTRANCES.md)）

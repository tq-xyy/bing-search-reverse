### 反复出现的根因（这是真正要记住的）

**「无区分度基线」**：在服务端本来就正常的时段做 A/B，两组都通过，
于是把「变量无效」当成结论。历史上**所有**错误结论都源于此。

对策：对照实验必须带哨兵（已知成功的组合同轮校验），且基线要与生产实现一致——
历史上 26 个脚本各自复制了 `h2get`，其中 `request-shape-check` 拼的 URL 甚至带了
生产明令禁止的 `&first=1`。复制品测的不是生产代码。

## 3. 协议层的关键结论

### 3.1 `sec-ms-gec`：从「唯一开关」到「可纯算法生成」

演进了四步，每步都推翻上一步的措辞：

1. 起初认为它是「富化模块的唯一开关」——不带就拿不到。
2. 后来发现 rdr 第二遍能兜底，降级为「可选加速层」。
3. 2026-10-15 定位到它由 Edge 网络栈注入（不是页面 JS），逆向出签名结构。
4. 2026-10-18 用 Frida 读函数参数，反汇编完成，**纯算法可生成**。

最终算法（与浏览器逐字节一致）：

```
PREFIX  = "Copyright (C) Microsoft Corporation. All rights reserved."   // 57 字节
SALT    = "NO_SUBSCRIPTION"
ticks   = ((unix + 11644473600) - ((unix + 11644473600) % 300)) * 10^7
payload = PREFIX + str(ticks) + SALT
part2   = SHA256(payload)                          // 64 hex
part1   = hex(hashA(c1,c2) XOR hashB(c1,c2))       // 16 hex
gec     = part1 + "-" + part2
```

- 轮换窗口 **300 秒**（同一窗口内所有请求共用一个值）。
- **只对 Edge UA 生效**；Chrome UA 带上也会被忽略。
- 版本头 `sec-ms-gec-version: 2-<Edge 版本>`，Bing 不校验版本号，只要求 `2-` 前缀。

**结论**：拿不到 GEC 时第一遍是骨架页（~105KB），但 rdr 第二遍仍能补救；
拿到则第一遍就是填充页（~~350~~480KB）。所以它是**加速层而非必需项**。

### 3.2 cookie 的三个独立开关

缺任何一个都降级，且**三个是独立的**（历史上曾把其中一个误记到另一个头上）：

| 开关                        | 形态要求                                                                 |
| --------------------------- | ------------------------------------------------------------------------ |
| `SRCHHPGUSR` 的渲染窗口字段 | `PREFCOL/BRW/BRH/CW/CH/DPR/UTC` 必须补全                                 |
| `_RwBf`                     | **必须完整形态**，简化版直接骨架页                                       |
| `HVE`                       | = 首页 HTML 的 `Salt:"..."`，需合并进已有 `SRCHHPGUSR`（不能追加同名项） |

### 3.3 UA

**UA 的浏览器族不是反爬变量**。真正决定填充/骨架的是上面的 cookie 完整度。
生成形态真实的 Edge UA 只为一个理由：不引入现实中不存在的指纹
（如 `Chrome/160 + Edg/131` 这种内核版本不一致的组合）。

## 4. 解析层的关键结论

### 4.1 为什么用 DOM 而不是正则

2026-10-17 前用「正则 + 深度计数扫描器」提取嵌套结构，三个 bug 都是深度计数错位。
2026-10-18 换 `htmlparser2` + `css-select`：外部依赖只多两个，但选择器可读、
嵌套结构不再需要手写状态机。

### 4.2 两套并存的 DOM 必须都认（实测都存在）

| 模块     | 形态 A                            | 形态 B                                 |
| -------- | --------------------------------- | -------------------------------------- |
| 答案摘要 | `cht`（AI Overview，`.cht_text`） | `gs`（Generative Summary，`.gs_text`） |
| 结果展开 | `b_rcGbMod`（hero + 卡片列表）    | `b_richcard`（tabs + b_vList）         |
| 资讯     | `nscjk_card_*`（嵌在结果流里）    | `nscard_*`（独立资讯块）               |
| 视频     | 视频卡 `li.b_vidAns`              | 主结果内嵌 `.rc_videocap`              |

### 4.3 时间字段按精度截断（2026-10-18 修）

旧实现把「6 天之前」反推后一律补成 `YYYY-MM-DD HH:mm`，等于把
「只知道是哪天」包装成「知道是 00:00」。实测污染证据：两个不同视频的
`published` 都是 `2026-08-19 06:50`——同一分钟内发起的查询里，
所有「x 小时前」条目共享同一分钟位。

现在 `day`→`YYYY-MM-DD`、`hour`→`YYYY-MM-DD HH`、`minute`→`YYYY-MM-DD HH:mm`，
并附 `*Precision` 字段。**字符串仍是前缀可比的**，排序不需转 Date。

### 4.4 `overview.paragraphs` 是 Markdown

列表转 `- ` / `1. `，嵌套列表缩进 4 空格，代码块保留围栏。
取正文时跳过引用链接与代码块工具栏（`cht_codblk_hdr`）。

⚠️ 旧实现曾「先 `a.children = []` 再取文本」——就地改写 DOM，
导致稍后取来源站名时拿到空串（知乎两条来源名曾因此为空）。现已改为视图层过滤。

## 5. 一次性观测（不作契约用，会随服务端漂移）

### 5.1 AI Overview 覆盖率

实测约 **8%~33%**，随查询类型剧烈波动。**不能用有无 overview 当质量信号**：
2026-10-23 的对照里，模糊查询的 overview 命中率反而更高（6/10 vs 5/10），
但其中 2 条内容是错的、1 条混入明确错误条目。
**它看起来像「直接答案」，比没有更误导。**

### 5.2 政经模糊化三组对照（2026-10-23）

10 条政经词，A 原词 / B 模糊词 / C 模糊词给沙盒：

| 组  | 条数 | overview | 耗时                 |
| --- | ---- | -------- | -------------------- |
| A   | 110  | 5/10     | 686ms/次             |
| B   | 116  | 6/10     | 643ms/次             |
| C   | —    | —        | 39.7s/次，758K token |

四条可复用的判断：

1. **Bing 从不「失败」，它只是去答另一个问题。** B 组零空结果、条数还多 5%。
2. **条数会骗人。** 14 条里至少 5 条是同一篇爆款文的转载。
3. **决定成败的是「锚点唯一性」。** 唯一专名（雅典/景德镇）几乎无损；
   但有更强替代语义时失败（「亚美尼亚问题」→ 1915 大屠杀）。
4. **沙盒的幻觉是「精确数字的合理插入」。** 混在一堆正确数字中间，
   文末还有局部诚实标注，反而提高可信度观感。**必须回源核。**

### 5.3 Agent 检索实验的可改进点

trace 只存 `meta`、不存工具返回内容，导致无法自动核验「答案里的数字是否来自它读到的页面」。
若 trace 存一份工具返回摘要（如首 2000 字符），核验成本会降一个量级。
